1. EXECUTIVE SUMMARY & PROBLEM STATEMENT
====================================================================================================
The Modern Student Dilemma:
Engineering students and technical learners today suffer from fragmented identity and workflow overload:
- Problem solving is scattered across LeetCode, CodeChef, Codeforces, HackerRank, and GeeksforGeeks.
- Open-source contributions and development work are trapped inside GitHub repositories.
- College attendance, internal marks, semester timetables, and fee dues live in obsolete ERP portals.
- Hackathons, competitive events, and tech workshops are scattered across Unstop, Devpost, and Meetup.
- Faculty coordinators lack authentic verification tools to track student achievements or validate projects.
- Recruiters struggle to separate authentic student builders from paper resumes.

The Solution: LynDesk
LynDesk is a unified, all-in-one Student Operating System that consolidates competitive coding analytics,
hackathon discovery, academic operations, AI study tooling, verified project portfolios, and recruiter
talent discovery into a single, high-performance, dark/light minimal digital headquarters.

Core Philosophy & Zero-Fabrication Mandate:
- 100% Empirically Grounded: No synthetic multipliers, no fake contest ratings, no mock data.
- Live Real-Time Aggregation: Real upstream GraphQL and HTML parsers pull genuine student metrics.
- Multi-Stakeholder Ecosystem: Serves Students, Faculty/Coordinators, Recruiters, and College Admins.

5. COMPLETE MODULE-BY-MODULE FUNCTIONAL BREAKDOWN
====================================================================================================

5.1 CODING DECK (The Competitive Programming Engine)
---------------------------------------------------
- What it does: Scrapes, normalizes, and aggregates live student metrics across 6 developer platforms.
- How it works:
  * LeetCode: Queries LeetCode's official GraphQL endpoint (`matchedUser`, `userContestRanking`,
    `submitStatsGlobal`, `tagProblemCounts`, `languageProblemCount`, `userCalendar`).
  * Codeforces: Queries official Codeforces REST API (`user.info`, `user.status`, `user.rating`).
  * CodeChef: Parses embedded JavaScript arrays (`var all_rating = [...]`) and HTML metadata to extract
    historical contest rating milestones, star ratings, and global/country ranks.
  * HackerRank & GeeksforGeeks: Parses profile endpoints to retrieve practice scores and rank badges.
  * GitHub: Queries GitHub REST API to compute total public repositories and annual commit pushes.
- Zero-Fabrication Guarantee: If a platform has 0 solves or no contest history, it shows an authentic
  empty state ("Unrated", "0 solves") without synthetic multipliers.

5.2 EVENT DESK & HACKATHON EXPLORER
-----------------------------------
- What it does: Centralized directory of technical competitions, hackathons, and webinars.
- How it works:
  * Pulls live hackathons from external feeds and internal coordinator broadcasts.
  * Tracks applied hackathons in `user_hackathon_applications` table.
  * Provides calendar synchronization to prevent deadline conflicts with exams or lectures.

5.3 COLLEGE DESK (Academic Hub)
-------------------------------
- What it does: Replaces legacy college ERP interfaces with a modern, responsive academic dashboard.
- How it works:
  * Manages daily timetables, period slots, faculty names, and lab rooms.
  * Computes subject-wise attendance percentages with color-coded safety margins (Green >= 75%, Red < 75%).
  * Calculates internal marks, midterm weightages, and projected semester SGPA.

5.4 STUDY DESK (AI-Powered Active Recall)
-----------------------------------------
- What it does: Turns static syllabus topics into interactive study modules and quizzes.
- How it works:
  * Sends curriculum prompts to Google Gemini API (`/api/study/generate-lessons`).
  * Generates interactive flashcards and multiple-choice quizzes.
  * Evaluates written answers using AI semantic comparison (`/api/study/grade-answer`), saving weak
    concepts to the `study_mistakes` table for personalized spaced repetition.

5.5 REAL-TIME WORKSPACES
------------------------
- What it does: Enables hackathon teams to coordinate tasks, files, and notes in real time.
- How it works:
  * Backed by `project_spaces`, `workspace_tasks`, `workspace_notes`, and `workspace_artifacts`.
  * Live user presence is powered by Supabase Realtime Channels (`workspace_presence` and WebSocket broadcast),
    updating member online status in sub-100ms.

5.6 VERIFIED STUDENT PORTFOLIO (WORKS)
--------------------------------------
- What it does: A verifiable proof-of-work showcase for student builders.
- How it works:
  * Students submit project repositories, live preview URLs, demo videos, and technical descriptions.
  * Supports peer star ratings (`student_work_ratings`) and view counters (`student_work_views`).
  * Coordinators can stamp institutional approval (`student_work_staff_reviews`), elevating projects
    to the college-wide public leaderboard.

5.7 COORDINATOR / FACULTY DESK
------------------------------
- What it does: Empowers college placement cells and professors to monitor and mentor students.
- How it works:
  * Review queue for academic credit applications (`credit_applications`).
  * Direct broadcast system (`staff_broadcasts`) with delivery receipts (`broadcast_receipts`).
  * One-click CSV export of student performance benchmarks.

5.8 RECRUITER RADAR
-------------------
- What it does: Connects verified top talent with tech companies and hiring partners.
- How it works:
  * Recruiters use authenticated API keys (`recruiter_keys`) to query `/api/recruiter/talent`.
  * Filter candidates by verified DSA solves, GitHub commits, and contest ratings.
  * Zero noise: Eliminates unverified claims by linking directly to live platform handles.

5.9 INSTITUTIONAL ADMIN & SECURITY AUDIT
----------------------------------------
- What it does: High-level administration for college deans, HODs, and system administrators.
- How it works:
  * Role-based access control (RBAC) across Students, Staff, Coordinators, and Admins.
  * Immutable institutional audit logging (`institutional_audit_logs`) tracking sensitive actions.

7. PLATFORM SCRAPERS & EXTERNAL INTEGRATIONS ENGINE
====================================================================================================

How Scrapers Handle Anti-Bot & Network Protections:
- User-Agent & Header Rotation: Standardized modern browser headers (`Mozilla/5.0 Chrome/122`) prevent
  abrupt bot blocks.
- Smart Cache & Rate-Limiting: Client-side localStorage handles provide instantaneous 0ms UI render,
  while server route handlers utilize `cache: "no-store"` with graceful fallback circuit breakers.
- Fallback API Proxies:
  * LeetCode: Primary GraphQL query -> Secondary public proxy (`leetcode-stats-api`) -> Alfa proxy fallback.
  * CodeChef: Primary API endpoint -> Direct HTML DOM regex extraction (`var all_rating = [...]`).
  * Codeforces: Direct official REST API (`user.info`, `user.status`, `user.rating`).
  * GitHub: Direct official REST API (`/users/{username}`, `/users/{username}/repos`, `/users/{username}/events`).

8. SECURITY, AUTHENTICATION & ROW LEVEL SECURITY (RLS)
====================================================================================================
1. Zero Auth Secret Leakage:
   - Supabase service role keys (`SUPABASE_SERVICE_ROLE_KEY`) are isolated exclusively to Server Route Handlers.
   - Client bundle only receives public keys (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`).

2. Multi-Tenant Row Level Security (RLS):
   - 100% of PostgreSQL tables have RLS enabled.
   - Policies strictly enforce `auth.uid() = user_id` on all write/update mutations.
   - Public data (events, verified works gallery) is guarded with read-only SELECT policies.

3. Strict Input Sanitization & Type Safety:
   - All URL parameters and handle inputs are normalized and stripped of dangerous characters.
   - Regex validation prevents SQL Injection (SQLi) and Cross-Site Scripting (XSS).

9. POTENTIAL PRESENTATION / VIVA QUESTIONS & WINNING ANSWERS
====================================================================================================

Q1: "Why did you build this as a web application instead of a mobile app?"
Answer:
"Engineering students and developers do the vast majority of their programming, project collaboration,
and academic work on desktop and laptop machines. Next.js 16 allows us to deliver a blazing-fast desktop
operating system experience while remaining 100% responsive and mobile-friendly on smartphones via Tailwind v4."

Q2: "How do you fetch data from LeetCode or CodeChef if they change their website structure?"
Answer:
"We built our data aggregation layer with a Multi-Tier Resilient Fallback Architecture. For LeetCode, we
query their official GraphQL API first; if blocked, our system automatically falls back to secondary and
tertiary REST endpoints. For CodeChef, we extract the core data directly from their embedded JSON payload
rather than brittle DOM selectors, ensuring long-term stability."

Q3: "Why choose Supabase and PostgreSQL over MongoDB or Firebase?"
Answer:
"LynDesk manages complex relational data: student profiles link to academic marks, workspaces contain
tasks and members, and works link to peer ratings and faculty reviews. PostgreSQL provides robust ACID
compliance and foreign key integrity. Furthermore, Supabase gives us built-in Row-Level Security (RLS)
and real-time WebSocket subscriptions without managing separate server infrastructure."

Q4: "How does the AI Study Desk work? Does it hallucinate?"
Answer:
"The Study Desk uses Google Gemini models constrained by strict prompt boundaries and JSON schemas.
Rather than allowing freeform generation, the model is fed structured curriculum topics and returns
strictly typed flashcards and rubric-based quiz evaluations. Student answers are graded against
deterministic engineering rubrics."

Q5: "What prevents a student from claiming someone else's LeetCode or GitHub profile?"
Answer:
"Our system uses Handle Verification Handshakes (`handle_verifications` table). In high-trust workflows
(such as recruiter searches or academic credit requests), students verify ownership by temporarily adding a
unique 6-character LynDesk verification token to their platform bio or public gist before linking."

Q6: "How do you ensure user data privacy between different colleges?"
Answer:
"All institutional data is multi-tenant partitioned using PostgreSQL Row-Level Security (RLS) policies
scoped to `college_id`. Students from College A can never read or query academic records, internal marks,
or staff broadcasts from College B."
