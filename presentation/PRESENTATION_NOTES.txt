1. EXECUTIVE SUMMARY & PROBLEM STATEMENT
====================================================================================================
The Modern Student Dilemma:
Engineering students and technical scholars today face severe fragmentation and workflow overload:
- Problem solving and contest statistics are scattered across LeetCode, CodeChef, Codeforces, HackerRank, and GeeksforGeeks.
- Open-source contributions and software engineering artifacts remain trapped in raw GitHub repositories.
- Daily college attendance, internal assessment marks, semester timetables, and fee payment receipts live inside antiquated, clunky legacy ERP portals.
- Hackathons, competitive events, and symposiums are scattered across Unstop, Devpost, and informal chat groups.
- Faculty coordinators and HODs lack authentic, automated verification tools to review student achievements, track daily period attendance, or record internal marks.
- Corporate recruiters struggle to separate authentic student builders from AI-embellished paper resumes.

The Solution: LynDesk
LynDesk is an enterprise-grade, all-in-one Student Operating System that consolidates competitive coding analytics, hackathon discovery, digital academic ERP operations, AI-powered active recall study tooling, verified project portfolios, faculty management loops, and corporate recruiter talent discovery into a single, high-performance, dark/light minimal digital headquarters.

Core Engineering Philosophy & Zero-Fabrication Mandate:
- 100% Empirically Grounded (Rule 19): Zero synthetic multipliers, zero fake contest ratings, zero mock fallback metrics. Every single metric and record is derived from live PostgreSQL rows or upstream API responses.
- Live Real-Time Aggregation: Resilient GraphQL queries, REST endpoints, and DOM parsers pull genuine student metrics with zero manual data entry.
- Multi-Stakeholder Ecosystem: Serves four distinct personas under unified role-based authentication:
  1. Students (Engineers & Scholars)
  2. Faculty Instructors & Academic Coordinators
  3. Corporate Recruiters & Talent Acquisition Partners
  4. Institutional Super-Administrators (Deans, Principals & Registrars)

8. SECURITY, AUTHENTICATION & ROW LEVEL SECURITY (RLS) DEFENSE GRID
====================================================================================================

1. Zero Auth Secret Leakage:
   - `SUPABASE_SERVICE_ROLE_KEY` and administrative secrets reside exclusively in Server Route Handlers.
   - Client bundles receive only public keys (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`).

2. Multi-Tenant Row-Level Security (RLS):
   - 100% of PostgreSQL tables enforce RLS policies.
   - Policies restrict write/update operations to `auth.uid() = user_id`.
   - Public feeds (events, verified works gallery) are governed by read-only SELECT policies.

3. Strict Zod Runtime Input Validation:
   - All POST/PATCH endpoints validate payloads and query parameters using strict Zod schemas.
   - Defense against SQL Injection (SQLi) and Cross-Site Scripting (XSS).

10. POTENTIAL PRESENTATION / VIVA QUESTIONS & WINNING ANSWERS
====================================================================================================

Q1: "Why did you build this as a web application instead of a mobile app?"
Answer:
"Engineering students and developers do the vast majority of their programming, project collaboration,
and academic work on desktop and laptop workstations. Next.js 16 allows us to deliver a high-performance
desktop operating system experience with keyboard shortcuts and multi-tab workflows, while remaining
100% reactive and responsive on mobile devices via Tailwind CSS v4."

Q2: "How do you fetch data from LeetCode or CodeChef if they change their website structure?"
Answer:
"We engineered a Multi-Tier Resilient Fallback Architecture. For LeetCode, we query their official GraphQL
API first; if blocked, our server automatically rotates to secondary and tertiary proxy endpoints. For CodeChef,
we extract data directly from their embedded JSON state variables rather than brittle DOM elements, ensuring
long-term resilience against frontend redesigns."

Q3: "Why choose Supabase and PostgreSQL over MongoDB or Firebase?"
Answer:
"LynDesk manages complex relational data: student profiles link to academic marks, workspaces contain
tasks and members, and works link to peer ratings and faculty reviews. PostgreSQL provides ACID compliance
and relational foreign key integrity. Furthermore, Supabase gives us built-in Row-Level Security (RLS)
and real-time WebSocket subscriptions without maintaining separate backend server infrastructure."

Q4: "How does the AI Study Desk work? Does it hallucinate?"
Answer:
"The Study Desk uses Google Gemini models constrained by strict prompt boundaries and JSON output schemas.
Rather than allowing unconstrained generation, the model receives structured curriculum topics and returns
strictly typed flashcards and rubric-based evaluations. Student answers are evaluated against deterministic
engineering rubrics, and weaknesses are logged into the `study_mistakes` table for spaced repetition."

Q5: "What prevents a student from claiming someone else's LeetCode or GitHub profile?"
Answer:
"Our system utilizes an AI Deduplication Sentinel and Handle Verification Handshakes (`handle_verifications` table).
When linking profiles, the system checks for existing database claims across platforms. In high-trust workflows
(such as recruiter shortlists or academic credit claims), coordinators verify ownership before granting verified badges."

Q6: "How do you ensure data privacy between different colleges?"
Answer:
"All institutional records are multi-tenant partitioned using PostgreSQL Row-Level Security (RLS) policies
scoped to `college_id`. Students and faculty from College A are cryptographically restricted from reading or
querying academic records, internal marks, fee schedules, or staff broadcasts from College B."

Q7: "How do the printable vouchers and candidate dossiers ensure authenticity?"
Answer:
"Every generated document (Fee Voucher, OD Pass, Grade Transcript, or Candidate Dossier) computes a dynamic
SHA-256 checksum and renders an embedded cryptographic QR code alongside official university seal metadata.
Print stylesheets (`@media print`) ensure crisp, standard A4 physical output without UI artifacts."
